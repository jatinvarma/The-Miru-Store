3. Introduction

The MIRU E-commerce Store is a full-stack, web-based platform tailored exclusively for curated objects, delivering a refined editorial aesthetic. The proposed system aims to provide users with an intuitive, minimalist interface for discovering and purchasing products online.

The core problem it aims to solve is the clutter and complexity found in traditional e-commerce platforms by prioritizing clean design and zero-friction navigation. Its main objectives include enabling seamless browsing, enforcing secure user authentication, providing persistent cart management, and streamlining reliable order processing.

4. Scope

Included Features:

  • User registration and login utilizing secure JWT sessions.
  • Full product catalog display with categorized filtering, free-text search, and dynamic price sorting.
  • A persistent shopping cart tied to individual user identities in the database.
  • A comprehensive checkout process resulting in logged order history.
  • A contact system for direct customer inquiries.

Out of Scope:

  • Active integration with live external payment gateways (e.g., Stripe, PayPal).
  • A comprehensive administrative web dashboard for live, on-the-fly inventory or user management.
  • Automated shipping tracking or multi-warehouse logistics handling.

5. Functional Requirements

  • FR1 - User Authentication: The system must allow new users to register, existing users to log in with an email/password combination, and assign a stateless JSON Web Token (JWT) to secure user sessions.
  • FR2 - Catalog Management: The system must fetch and display the product listing dynamically. The application must interpret search string inputs and filter elements reflecting keyword matches or categorical bounds.
  • FR3 - Cart Operations: Authenticated users must be able to insert valid products into a persistent shopping cart, edit their purchase quantities, and completely discard cart entries without resulting errors.
  • FR4 - Order Processing: The system must provide a mechanism for users to confirm their cart contents, compile a total subtotal, log an order schema into the database, and immediately clear the user's active cart.
  • FR5 - Contact Form: Any visitor must be able to submit a textual message with their email and name, which the backend API will intercept and store inside the database for query via DB administrators.

6. Non-Functional Requirements

  • Reliability: Standard execution routines must depend on robust SQLite transaction boundaries to ensure zero data corruption during simultaneous endpoint queries.
  • Usability: The platform mandates intuitive interactions, stipulating less than 3 user clicks to initiate the addition of a displayed product into a personal cart.
  • Performance: The application UI must not demonstrate visual lagging, while routine REST API responses for database fetches need to reliably fire in under 250 milliseconds.
  • Security: All user passwords must undergo irreversible bcrypt hashing upon account creation. All personal endpoints (carts, orders) must invoke middleware to parse JWT Bearer validation protocols preventing unauthorized lateral access.
  • Scalability: Designed using stateless authentication, the primary Express.js node application must be structured effectively to scale horizontally if transition to a distributed SQL cluster is mandated later.

7. Constraints

  • Time/Process Constraints: Development iterations utilize rapid deployment templates utilizing a build-less React CDN injection to reduce setup overhead.
  • Technology Limitations: Data storage relies solely on an encapsulated local SQLite environment. While excellent for localized testing and low traffic, concurrent volume writes are physically bounded by file locks.
  • Budget Limitations: As a conceptual build, live domain or third-party SSL, CDN routing dependencies are restricted for subsequent iteration cycles.

8. Acceptance Criteria

  • Authentication Accuracy: A user's profile successfully generates; subsequent login validations with incorrect passwords must explicitly fail.
  • Cart Persistence: Verified users actively retaining items inside their cart must observe those identical items returning after terminating their session and returning the following day.
  • Order Fulfillment Logic: Completing a valid checkout forces the exact replication of the cart total to the final order, simultaneously issuing a Cart Wipe command preventing duplicate order queries.

9. User Interface Requirements

The system design pivots on minimalism combined with high-impact editorial motifs.

  • Layout: Employing a Single Page Application canvas mapping. Critical menus (like the shopping cart) must initiate via dynamic, sliding off-screen modal drawers minimizing rigid URL transitions.
  • Color Scheme: Monochromatic dominance prioritizing white space (`#ffffff` and `#fcfcfc`), starkly contrasted by deep charcoal texts (`#121212`).
  • Typography: Imposing refined Serif fonts ("Cormorant") for large visual headers, balanced appropriately by utilitarian Sans-Serifs or Monospace ("DM Mono") variables for numerical or interactive data points.
  • User Experience: Transitions demand micro-animations (hover opacities on image grids, smooth scaling interactions, real-time cart update toasts) ensuring organic engagement responses.

10. Use Cases

  • UC1 - Searching the Catalog:
    Scenario: A guest accesses the index. They type "ceramic" into a search form. The UI state synchronously scans available products, filtering non-match components and immediately displaying ceramic items visually without triggering a browser refresh.
  • UC2 - Finalizing an Order:
    Scenario: A logged-in user with 3 items in their cart opens their cart drawer and selects "Checkout/Place Order". The API intercepts this payload, verifies data integrity against the DB, clones the totals into a sealed Order item, returns a success notification to the UI, and renders the cart empty.
  • UC3 - Invalid Access Attempt:
    Scenario: A malicious external request attempts to fetch URL /api/orders using cURL, omitting valid headers. The system instantly halts the router protocol, denying database interaction and returning a standard 401 Unauthorized error code.

11. Data Requirements

  • Data Types & Sources: String arrays, Integers (prices/quantities), and Timestamp structures. Inputs trigger exclusively from client-side interaction queries and defined seed product logic inside the application core.
  • Storage Requirements: Centralized sequentially to a local SQL file structure (shop.db), establishing rigid relational integrity across User, Product, Cart, Order, and Contact tables.
  • Data Management: Responses and payloads traverse the HTTP channel rigidly via structured JSON formatting. Passwords exclusively exist in memory hashed configurations during storage schemas.

12. System Architecture

The system leverages a decoupled frontend/backend dual-tier configuration:

  • Frontend Component Layer: Orchestrated completely by React 18, utilizing functional components and hooks to manipulate local logical states while dispensing fetch operations dynamically to backend endpoints.
  • Backend Routing Layer: Run on Node.js/Express.js, the backend strictly dictates business flow logic—catching requests, parsing JSON limits, checking access rights via JWT verification nodes.
  • Database Layer: Interconnected intimately with the backend via the better-sqlite3 driver to ensure immediate synchrony on data fetching protocols without asynchronous dependency hell.

13. Technical Requirements

  • Software & Environment: Node.js runtime environment (v16.14.0 or greater).
  • Dependency Packages:
    • Server side: express, better-sqlite3, bcryptjs, jsonwebtoken, cors.
    • Client side: React and ReactDOM implemented via explicit unpkg CDN nodes.
  • Hardware Constraints: Effectively scalable on minimal 1 Core Virtual Private Servers utilizing 512 MB of dynamic memory resources.
